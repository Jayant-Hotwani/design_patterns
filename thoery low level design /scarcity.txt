SCARCITY - FULL THEORY (SEMAPHORES, RESOURCE POOLING, PATTERNS, UTILIZATION)
==============================================================================


PART 1: SEMAPHORES VS. RESOURCE POOLING
==============================================================================

THE UNIVERSAL SHAPE OF EVERY SCARCITY PROBLEM
-----------------------------------------------------
Every scarcity problem comes down to enforcing a capacity limit and
deciding what happens when you hit it. Three things always need to
happen, regardless of which tool you use:

1. Track how many resources are currently in use.
2. Block new requests once the limit is hit.
3. Wake waiting threads when a resource frees up.

Semaphores and resource pools are just two different SHAPES of the same
underlying mechanism.


SEMAPHORES - PERMISSION WITHOUT AN OBJECT
-----------------------------------------------------

The core distinction

A semaphore gives you permission to proceed - a green light - but it
doesn't hand you any specific thing. It's purely a counter:

    Permits = 5 at start.
    acquire() -> permits-- (blocks if already 0)
    release() -> permits++

The nightclub analogy

"The club holds 100 people. The bouncer has 100 tokens. When you want to
enter, you need to get a token from the bouncer... If all 100 tokens are
out when you arrive, you wait."

The token itself doesn't correspond to a specific chair, a specific spot
on the dance floor, or a specific anything inside the club. It's just
proof that "one of the 100 available slots is currently yours." You
could stand anywhere inside - the token doesn't tie you to a particular
resource. It only tracks COUNT, not IDENTITY. This is the exact
distinguishing feature that separates a semaphore from resource pooling.

Walking through the APIClient code

    #include <semaphore>

    class APIClient {
    private:
        std::counting_semaphore<5> requestPermits{5};

    public:
        Response makeRequest(const std::string& endpoint) {
            requestPermits.acquire();
            try {
                auto response = httpClient.get(endpoint);
                requestPermits.release();
                return response;
            } catch (...) {
                requestPermits.release();
                throw;
            }
        }
    };

- std::counting_semaphore<5> requestPermits{5}; - declares a semaphore
  whose MAXIMUM permit count is 5 (the template parameter), initialized
  with 5 permits available right now (the constructor argument).
- requestPermits.acquire(); - the "get a token from the bouncer" step.
  If fewer than 5 requests are in flight, returns immediately. If 5 are
  already out, blocks - the thread sleeps (futex-based), consuming zero
  CPU, until someone calls release().
- httpClient.get(endpoint) - the actual work, with a permit secured.
  Nothing about the semaphore knows or cares WHICH request this is - it
  just knows "one of my 5 slots is occupied."
- requestPermits.release(); (both paths) - the permit gets returned
  whether the request succeeds or throws.

Why this fits "an API client limiting concurrent requests"

There's nothing to hand out here - no pre-created "Request" objects
waiting in a queue. Each call creates its own HTTP request fresh; the
only thing being limited is the COUNT of how many can run
simultaneously. This is the signature of a pure semaphore problem: you're
capping concurrency, not managing a finite set of pre-existing, reusable
objects.

Challenges - the interviewer's favorite trap

"What happens if an exception is thrown? This is the #1 bug they're
testing for."

If httpClient.get(endpoint) throws and there's no catch block releasing
the permit, that permit is gone forever - the semaphore's internal
counter never gets incremented back, permanently shrinking your
effective concurrency limit by one, every time this happens. Do this
enough times and eventually all 5 permits are silently lost, and
acquire() blocks forever for everyone - the exact "everything looks
fine, nothing works, zero errors in monitoring" failure mode, just
manifesting through a semaphore instead of a connection queue.

"Since C++ lacks finally blocks, you must manually release in catch
blocks or use RAII wrappers."

Languages like Java have a finally block that runs no matter what
(success, early return, or throw) - making "always release" trivial. C++
has no finally, so you either duplicate the release call in both the
success path and every catch block, or use an RAII wrapper (a guard
object whose destructor calls release() automatically, so it happens
even during stack unwinding) - the same RAII philosophy behind
lock_guard/unique_lock for mutexes.


RESOURCE POOLING - PERMISSION PLUS AN ACTUAL OBJECT
-----------------------------------------------------

Where semaphores stop being enough

"Connection pools have a different problem than simple concurrency
limiting. You don't just need to cap how many connections are in use.
You need to hand out the actual connection objects themselves."

A database connection isn't interchangeable in the way "one of 100
nightclub slots" is - each connection is a SPECIFIC object: it has its
own open socket, its own authentication state, potentially its own
in-progress transaction. You can't just tell a thread "you have
permission to use a connection" - you have to tell it WHICH one, and
hand over the actual object, because:

1. You can't create new ones on demand - establishing a connection is
   expensive (memory, file descriptors, handshake time), so you must
   reuse a small, fixed set of pre-created objects.
2. The object itself carries state - unlike a nightclub token (fungible
   - any token is as good as any other), a specific Connection* might be
   mid-transaction or have specific session state that matters.

Why a blocking queue is the natural fit

"When a thread needs a connection, it pulls from the queue. If the queue
is empty because all connections are checked out, the thread blocks.
When another thread finishes, it returns the connection to the queue,
waking one waiting thread."

availableConnections (a std::queue<Connection*>) holds the actual
objects currently free to hand out. acquire() pulls a specific object
out (and returns THAT EXACT POINTER to the caller - not just a
"permission granted" signal). release() puts a specific object back.

    Semaphore:        acquire() -> (nothing) -- just permission
    Resource pool:     acquire() -> Connection* conn -- an actual object, THIS one

SIDE-BY-SIDE: WHEN TO REACH FOR WHICH TOOL
-----------------------------------------------------
                            Semaphore                Resource Pool (Blocking Queue)
What you get from acquire  Nothing - just permission  A specific object (e.g. Connection*)
Are slots interchangeable  Yes - any permit identical  No - each object may carry its own
                           to any other                state (socket, auth, transaction)
Can you create more on     N/A - nothing to create,    No - objects are expensive to
demand?                    just a count                 create, must be reused
Example use case           API rate limiting,           Database connection pools, GPU
                           download concurrency caps    scheduling, thread pools
Underlying mechanism       Atomic counter + futex-based Mutex + condition variable
                           blocking                     guarding an actual queue of objects

The one-question test: "When a thread is granted access, does it need a
specific object, or just a green light?"
- "just a green light" (e.g., "you may make an API call now") -> Semaphore
- "it needs THIS PARTICULAR pre-existing, expensive-to-create object"
  (e.g., "here's connection #3, with its own socket and session")
  -> Resource pool


PART 2: RESOURCE POOLING CHALLENGES, PATTERNS, AND UTILIZATION
==============================================================================

CHALLENGES OF RESOURCE POOLING
-----------------------------------------------------

Upfront vs. Lazy Initialization

    Upfront: create all N connections in the constructor, right away.
    Lazy:    create connections one at a time, only when actually needed,
             up to a max of N.

Upfront means startup takes longer, but every request afterward is
uniformly fast - the connection it needs already exists. Lazy means the
service starts up instantly, but the FIRST N requests each pay the cost
of establishing a brand-new connection on the spot, making them slower.

Default to upfront in interviews - lazy initialization reintroduces the
"check-then-act" correctness bug: if two threads both see "no connection
exists yet, I need to create one" at the same time, without careful
locking, you could create more connections than allowed. Upfront
sidesteps this entirely: all N connections exist before any thread ever
asks for one.

Connection Validation (Handling Stale Connections)

A Connection* sitting in the pool's queue isn't guaranteed to still be
alive - the database might have closed it due to inactivity, the
network might have dropped, or it could just be broken. If you hand out
a stale connection without checking, the caller's query fails
unexpectedly.

The fix: validate before handing out. When acquire() is about to return
a connection, test it first (e.g., a trivial SELECT 1). If it's dead,
discard it and create a fresh replacement instead of returning the
broken one. Adds complexity but prevents confusing, intermittent
failures.

The Unbounded Queue Trap - Again

"The biggest pitfall is forgetting that the queue has finite capacity...
Always pass a capacity in the constructor."

If you create connections lazily and forget to cap the queue's maximum
size, nothing stops it from growing indefinitely - defeating the entire
purpose of a POOL (a fixed, bounded set of expensive objects). Fix:
always construct the queue with an explicit capacity matching your
intended pool size.

Blocking Forever on Request Paths - The Timeout Fix

acquire()'s plain wait() has no time limit - if all connections are
stuck, every new request blocks FOREVER, invisible to your own
monitoring, even though users experience timeouts on the outside.

Walking through ConnectionPoolWithTimeout

    Connection* acquire() {
        std::unique_lock<std::mutex> lock(mtx);
        if (!cv.wait_for(lock, timeout, [this] { return !availableConnections.empty(); })) {
            throw std::runtime_error("No connection available within timeout");
        }
        Connection* conn = availableConnections.front();
        availableConnections.pop();
        return conn;
    }

The only real change: cv.wait() becomes cv.wait_for(lock, timeout,
predicate). Behaves identically to wait() if a connection becomes
available within timeout - returns true, proceeds normally. But if
timeout elapses with the predicate still false, wait_for returns false,
and the code explicitly throws rather than continuing to wait.

This gives calling code an actual decision point:

    try {
        Connection* conn = pool.acquire();
        // use it
    } catch (const std::runtime_error& e) {
        // return a 503 to the user, retry, log and fail gracefully
    }

Instead of a thread silently hanging forever, you get an explicit,
catchable failure - the difference between a service that degrades
gracefully under load versus one that silently locks up.

Choosing the Timeout Value

"A decent heuristic is to add some buffer to your expected operation
time. Database queries run in 100ms? Set a 500ms timeout."

Timeout should be longer than normal variance, but still well under
whatever the caller's own patience/timeout is. Too short and you reject
requests that would have succeeded with a bit more patience. Too long
and a user sits watching a spinner while you optimistically wait for a
connection that, if something's really broken, is never coming - better
to fail fast than let the user's client give up first while your thread
is still stuck waiting for nothing.

Fairness - Who Gets the Connection First?

Condition-variable-based waiting is typically approximately FIFO but
doesn't strictly guarantee it. If you need a hard guarantee, some
blocking queue implementations offer a fair=true construction option
enforcing strict FIFO ordering - at the cost of reduced throughput. For
a typical connection pool, approximate fairness is usually fine.


COMMON PROBLEMS - THE THREE (PLUS ONE) RECOGNIZABLE SHAPES
-----------------------------------------------------

1. LIMIT CONCURRENT OPERATIONS - Pure Semaphore

Signature: "limit to N concurrent X," where there's no actual object
being handed out - just a cap on how many things can happen
simultaneously.

    class DownloadManager {
    private:
        std::counting_semaphore<3> downloadSlots{3};

    public:
        void download(const std::string& url, const std::string& destination) {
            downloadSlots.acquire();
            try {
                auto data = httpClient.download(url);
                std::ofstream file(destination, std::ios::binary);
                file.write(reinterpret_cast<const char*>(data.data()), data.size());
                downloadSlots.release();
            } catch (...) {
                downloadSlots.release();
                throw;
            }
        }
    };

Structurally identical to APIClient - acquire() before the operation,
release() in both success and exception paths. No pool of pre-created
"download slot" objects - the semaphore is purely tracking a count. Any
thread can perform any download; nothing ties a specific download to a
specific pre-existing resource object.

Recognizable examples: rate-limited API wrappers (cap concurrent calls),
image processing pipelines (cap concurrent CPU-heavy transforms), video
transcoding services (cap concurrent CPU/memory-intensive jobs) - in
every case, "no more than N at once," with no specific object changing
hands.

2. LIMIT AGGREGATE CONSUMPTION - Semaphore With Variable-Sized Permits

"The key difference from limiting concurrent operations is that
operations have different sizes. You're not just tracking '5 uploads in
flight.' You're tracking '47 MB of bandwidth currently in use.'"

Instead of every operation consuming exactly 1 permit, here each
operation consumes a VARIABLE number of permits, proportional to how
much of the actual resource it uses.

    class DiskWriter {
    private:
        static constexpr int MB = 1024 * 1024;
        std::mutex mtx;
        std::condition_variable cv;
        int available = 100; // 100 MB

    public:
        void writeFile(const std::vector<char>& data, const std::string& path) {
            int permits = std::max(1, (int)((data.size() + MB - 1) / MB));

            {
                std::unique_lock<std::mutex> lock(mtx);
                cv.wait(lock, [this, permits] { return available >= permits; });
                available -= permits;
            }

            try {
                std::ofstream file(path, std::ios::binary);
                file.write(data.data(), data.size());
            } catch (...) {
                std::lock_guard<std::mutex> lock(mtx);
                available += permits;
                cv.notify_all();
                throw;
            }

            std::lock_guard<std::mutex> lock(mtx);
            available += permits;
            cv.notify_all();
        }
    };

Key line:
    int permits = std::max(1, (int)((data.size() + MB - 1) / MB));
Computes how many megabytes this specific file needs, rounded UP to the
nearest whole MB (the "+ MB - 1" before dividing is the standard
"round up" trick), with a floor of at least 1 permit even for tiny files
(so a 10-byte file still consumes 1 permit, preventing unlimited tiny
writes from bypassing the budget).

    cv.wait(lock, [this, permits] { return available >= permits; });
    available -= permits;

Instead of checking "is available non-zero," this checks "is available
at least as large as what I SPECIFICALLY need." A 50 MB file waits until
50 full MB of budget is free; a 2 MB file only needs 2 MB free.

Hand-built with a raw mutex + condition variable rather than
std::counting_semaphore, because C++'s semaphore doesn't easily support
a variable-sized acquire/release computed per-call.

Notice notify_all() rather than notify_one() - different waiters need
different amounts. If you only woke one waiter, and its request needs
more permits than just freed up, it rechecks, sees it still isn't
enough, and goes back to sleep - while a different, SMALLER waiter that
could have proceeded right now never got the chance to check. Waking
everyone lets every waiter independently reassess whether its own
specific requirement is now satisfied.

Recognizable examples: bandwidth/in-flight-data limiting (cap total MB
uploading, not the COUNT of uploads), memory budgets for buffers (cap
total MB allocated across all threads, where each thread's buffer might
be a different size). Tell: the phrasing involves a quantity/measurement
(MB, GB, bytes) rather than a plain count of operations.

3. REUSE EXPENSIVE OBJECTS - Blocking Queue (Resource Pool)

"The key difference from the previous patterns is that you're managing
actual stateful objects, not just counting operations or tracking
resource units."

A database connection has an open socket and session state. A GPU has
loaded model weights sitting in VRAM. A file handle points to a specific
OS-level file descriptor. None of these are interchangeable in the way
"one of N permits" is - you can't just say "you may proceed," you have
to say "here is THIS SPECIFIC connection/GPU/handle, use it, then give
it back."

GPU Task Scheduler example: BlockingQueue holding exactly 4 GPU
references, inference requests take one, run their model, return it -
structurally identical code shape to the connection pool, just a
different kind of expensive object being managed.


MAXIMIZING UTILIZATION - GOING BEYOND "DON'T EXCEED THE LIMIT"
-----------------------------------------------------

This introduces a genuinely different GOAL from everything before it.
Governance (semaphores, bounded pools) answers "how do I stop threads
from exceeding a limit?" Utilization answers a different question:
"given a fixed, limited set of resources, how do I make sure they're
actually being used as much as possible, rather than sitting idle while
work waits?"

Motivating example: a connection pool might report "10 connections in
use" - sounds like full utilization - but if 9 of those connections are
attached to threads just sitting there doing application-level work
(parsing results, waiting on other computation) rather than actually
querying the database, the database itself is barely being touched even
though the pool looks "full." The resource is scarce AND underused
simultaneously.

Work Stealing

"Instead of a single queue feeding all workers, each worker maintains
its own queue. When a worker's queue empties, it steals tasks from
another worker's queue."

Picture 4 workers, each with their own personal task queue instead of
one shared queue. If Worker A gets stuck on one really long task while
Workers B, C, D finish quickly and go idle, a single-shared-queue design
would have B, C, D sit idle - but with work stealing, an idle worker can
reach into another worker's queue and grab a task waiting there. This is
what Java's ForkJoinPool and Go's scheduler do internally - shines when
task durations vary wildly (many short tasks mixed with occasional long
ones).

Batching

"If you're making 1000 small database writes, acquiring and releasing a
connection 1000 times wastes cycles on pool management."

Every acquire()/release() pair has real overhead - locking, condition
variable signaling, context switches under contention. Batching groups
many small operations into fewer, larger ones: instead of acquiring a
connection 1000 times to write 1000 rows one at a time, acquire it ONCE,
write all 100 (or 1000) rows in that single checkout, then release once.
Tradeoff: LATENCY for THROUGHPUT - an individual item might sit around
waiting to be grouped (adding delay for that one item), but the system's
overall rate of useful work per second goes up.

Adaptive Sizing

"A fixed pool of 10 connections might be too small during peak traffic
and wasteful during quiet periods."

A static pool size is a compromise - too small, becomes a bottleneck
during spikes; too large, wastes resources during quiet periods.
Adaptive pools grow when observed utilization is consistently high, and
shrink when connections sit idle - HikariCP (Java) and pgbouncer
(Postgres) implement this. Tradeoff: tuning difficulty - grow too
aggressively and you overwhelm the database during a spike; shrink too
quickly and you repeatedly pay connection setup costs.

When This Section Actually Matters in an Interview

"For most interviews, governance... is what they're testing. But if the
interviewer pushes on throughput..."

Most scarcity questions test whether you correctly reach for a semaphore
or bounded resource pool, handle exception-safety and timeouts properly,
and avoid classic pitfalls. Utilization techniques (work stealing,
batching, adaptive sizing) are a FOLLOW-UP DEPTH SIGNAL - worth
mentioning if the interviewer steers toward "how do you maximize
throughput" or "how would you keep the GPUs fully utilized," especially
at infrastructure-heavy, trading, or AI-lab-style interviews.


THE DECISION TREE, AS A CHECKLIST
-----------------------------------------------------
1. What's the goal - governance (don't exceed limits) or utilization
   (don't waste capacity)?

   If GOVERNANCE:
   2. Are you handing out actual stateful objects (connections, GPUs)?
      YES -> BlockingQueue as a resource pool
      NO  -> is it a plain count, or a variable-sized quantity?
             Plain count (concurrent operations)     -> Semaphore with N permits
             Variable quantity (MB, bandwidth, etc.)  -> Semaphore where permits = resource units

   If UTILIZATION:
   3. What's the shape of the inefficiency?
      Uneven task duration      -> Work stealing
      Many small operations     -> Batching
      Variable load over time   -> Adaptive sizing


THE RECURRING BUG CHECKLIST (WORTH MEMORIZING)
-----------------------------------------------------
Bug: Permits leaked forever
  Cause: Forgetting release() in an exception path
  Fix: Always wrap in try/catch/release, or use RAII

Bug: Unbounded memory growth
  Cause: Creating a queue with no capacity limit
  Fix: Always pass an explicit capacity

Bug: Silent, invisible hangs
  Cause: Blocking (take()/acquire()/wait()) with no timeout on a request path
  Fix: Use the timeout variant (poll(timeout), wait_for, tryAcquire(timeout))
       and fail gracefully

Bug: Exceeding the intended limit
  Cause: Check-then-act without proper locking (a correctness bug hiding
         inside a scarcity solution)
  Fix: Ensure the acquire/decrement step is itself atomic - which
       semaphores and the mutex-protected pool queue both guarantee by
       construction

This closing checklist is the payoff of the whole scarcity article: the
concepts (semaphore vs. pool, governance vs. utilization) let you
RECOGNIZE the shape of a problem quickly, but the actual bugs
interviewers probe for are almost always one of these four - the same
four failure modes that recur throughout concurrency generally: leaked
resources, unbounded growth, invisible blocking, and races on the
bookkeeping itself.
