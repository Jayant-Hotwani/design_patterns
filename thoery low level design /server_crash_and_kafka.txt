SERVER CRASH VS SUCCESSFUL SIGNUP, AND WHAT KAFKA IS FOR
============================================================


PART 1: HOW CAN A SERVER CRASH BUT THE USER STILL GOT A SUCCESSFUL SIGNUP?
============================================================

THE SHORT ANSWER
-----------------------------------------------------
Yes - it's genuinely possible for the user to see "signup successful!"
and then, a moment later, the server crashes BEFORE the background task
(sending the welcome email) ever actually runs. The user's account WAS
created (that part succeeded, for real, in the database). But the
welcome email might never get sent, because the task describing "send
this email" was sitting in an in-memory queue - and if the whole process
crashes, everything sitting in memory, including that queue, disappears
instantly, with nothing left behind.

WALKING THROUGH THE EXACT SEQUENCE
-----------------------------------------------------
    void signup(const std::string& email, const std::string& name) {
        userRepository.save(email, name);   // Step 1: written to the DATABASE - durable, survives a crash

        {
            std::unique_lock<std::mutex> lock(mutex_);
            not_full_.wait(lock, [this] { return emailQueue_.size() < MAX_SIZE; });
            emailQueue_.push({email, "welcome", name});   // Step 2: pushed into an IN-MEMORY queue
            not_empty_.notify_one();
        }
        // Step 3: function returns -> user sees "signup successful!"
    }

    Timeline:

    t0:  userRepository.save(email, name)     <- written to disk/DB. Permanent.
    t1:  emailQueue_.push(...)                <- sits in RAM only, nothing written to disk
    t2:  signup() returns -> user sees success message
    t3:  *** SERVER CRASHES / PROCESS KILLED ***
    t4:  emailWorker() never got a chance to pull the task and send the email
         -> the task that was sitting in emailQueue_ is GONE FOREVER
            (RAM is wiped when the process dies)

The user's account genuinely exists in the database - that part is safe,
because userRepository.save(...) wrote it to persistent storage (a
database survives a crash; it's on disk, not just in memory). But the
email task was never written anywhere durable - it only ever lived
inside emailQueue_, which is just a std::queue sitting in the process's
RAM. The instant the process dies (crash, server reboot, out-of-memory
kill, deployment restart - anything that kills the running program),
everything in that in-memory queue vanishes, because RAM contents don't
survive a process ending.

WHY THIS IS A REAL, MEANINGFUL GAP IN THE DESIGN
-----------------------------------------------------
This is one of the most important practical weaknesses of the simple
in-memory blocking queue pattern.

    What's durable (survives a crash):
    - Data written to a database
    - Data written to disk/files

    What's NOT durable (lost on crash):
    - Anything sitting only in an in-memory std::queue
    - In-flight messages an actor's mailbox hasn't processed yet
    - Any task a worker hasn't picked up and finished yet

So the honest picture is: "the user got a successful response" only
guarantees the parts of the operation that were actually completed and
made durable before responding - it says nothing about background work
that was merely QUEUED but not yet DONE.

HOW REAL SYSTEMS ACTUALLY HANDLE THIS
-----------------------------------------------------
This exact problem is precisely why production systems don't just use a
plain in-memory queue for anything that actually matters - they use
durable/persistent queues instead, like Kafka, RabbitMQ, SQS, or a
database-backed job table. The core idea: instead of
emailQueue_.push(...) just sitting in RAM, the "please send this email"
task itself gets written to disk (or to a separate durable message
broker) before signup() returns.

    Durable version of the same idea:

    t0:  userRepository.save(email, name)          <- written to DB
    t1:  messageBroker.publish("send-email", ...)   <- ALSO written durably
                                                        (Kafka/SQS/DB table - survives a crash)
    t2:  signup() returns -> user sees success

    t3:  *** SERVER CRASHES ***

    t4:  New server instance starts up, or the message broker still has the message
    t5:  A worker (possibly on a totally different machine) picks up the "send-email"
         task from the durable broker and processes it -> email STILL gets sent,
         even though the original server crashed

With a durable queue, even if the exact server that handled the original
signup request crashes immediately afterward, the "send an email"
instruction itself survives (because it was written to something
persistent, not just kept in that one process's RAM) - so some worker,
possibly a completely different machine, can still pick it up later and
finish the job.

THE TAKEAWAY
-----------------------------------------------------
The in-memory blocking queue pattern is genuinely great for decoupling
slow work from the request path and smoothing bursts - but it comes with
an honest tradeoff: if the whole process crashes between "task got
pushed to the queue" and "a worker actually finished processing it,"
that task is silently lost, with no error, no retry, nothing - because it
only ever existed in volatile memory. Whether that's an acceptable risk
depends entirely on what the background task actually does: losing a
marketing email occasionally might be tolerable; losing a "charge this
customer's card" task or a "ship this order" task would not be - which is
exactly why systems handling anything critical reach for a PERSISTENT
message queue instead of a plain in-memory one.


PART 2: WHAT IS KAFKA, AND WHY DO WE NEED IT?
============================================================

THE PROBLEM WE JUST DISCOVERED
-----------------------------------------------------
An in-memory queue (std::queue sitting in one process's RAM) disappears
the instant that process crashes. Any task waiting in it - like "send
this welcome email" - is lost forever, silently, with no error.

Kafka's entire reason for existing is to fix exactly this problem: it's
a queue-like system that writes messages to disk and keeps them safe,
even if the process that put them there crashes, and even if the process
that's supposed to read them crashes too.

THE SIMPLEST POSSIBLE DESCRIPTION
-----------------------------------------------------
Think of Kafka as a durable, shared "logbook" that many different
programs can write to and read from, instead of each program keeping its
own private, in-memory std::queue.

    Without Kafka:                          With Kafka:

    Your server's RAM                       Kafka (a separate system,
    +-------------------+                   running on its own machine(s),
    |  emailQueue_       |                  writing everything to DISK)
    |  [task1][task2]    |                  +----------------------------+
    +-------------------+                   |  "email-tasks" topic       |
        |                                   |  [task1][task2][task3]...  |
        v                                   +----------------------------+
     If this process dies,                       |                    |
     tasks are GONE.                       Your server writes    A worker (maybe
                                            tasks here.           on a totally
                                                                  different machine)
                                                                  reads from here.

                                            If your server crashes, the tasks are
                                            STILL SAFE inside Kafka, written to
                                            disk, waiting for someone to read them.

CONCRETELY, WHAT DOES KAFKA ACTUALLY DO?
-----------------------------------------------------
1. You "publish" a message to Kafka instead of pushing it onto your own
   in-memory queue.

       kafka.publish("email-tasks", {email: "john@example.com", template: "welcome"})

2. Kafka writes that message to disk (not just RAM) on its own servers,
   and typically keeps multiple copies across multiple machines (called
   "replication") - so even if one Kafka machine crashes, the message
   still exists on other machines.

3. Separately, one or more "worker" programs subscribe ("consume") from
   Kafka and read messages out, one at a time (or in batches), whenever
   they're ready.

       message = kafka.consume("email-tasks")
       sendEmail(message.email, message.template)

The key insight: your web server (the one handling signups) and the
worker (the one sending emails) don't even need to be the same program,
or even running at the same time. Your web server can publish a message
and immediately move on - it doesn't wait for the email to be sent, and
it doesn't even need the worker to be alive right that second. Kafka just
holds onto the message safely until some worker eventually comes along
and reads it - even if that's 5 seconds later, or even if your original
web server crashed 2 seconds after publishing.

WHY NOT JUST USE A REGULAR DATABASE TABLE INSTEAD?
-----------------------------------------------------
You might reasonably ask: "why not just insert a row into a database
table like pending_emails, and have a worker poll that table?" That
would actually work, and in smaller systems, this IS a completely valid
approach. Kafka becomes valuable specifically when:

- You have a lot of messages, very fast (thousands to millions per
  second) - a database table isn't built for that kind of raw throughput
  of "insert, then immediately read and delete."
- Multiple different systems need to read the same stream of messages
  independently. For example, maybe you want the SAME "user signed up"
  event to trigger three different things: send a welcome email, update
  an analytics dashboard, and notify a fraud-detection system. With
  Kafka, all three of those can independently subscribe to the same
  stream and each read every message, at their own pace, without
  stepping on each other.
- You want messages processed roughly in the order they arrived, at
  scale, across many machines.

A SIMPLE ANALOGY
-----------------------------------------------------
Imagine a shared, permanent notice board at a company, instead of
everyone shouting messages at each other directly:

- Anyone can walk up and pin a new notice to the board (a "publish").
- Multiple different departments can each read through the board at
  their own pace, and they don't erase notices when they read them - the
  notice stays up (Kafka doesn't delete a message just because one
  reader read it) so other departments can still come read it too.
- Even if one department's office burns down (crashes), the notice board
  itself is fireproof (durable, written to disk, often copied across
  multiple boards) - so when that department rebuilds and comes back,
  the notices are all still there waiting.

CONNECTING BACK TO THE SIGNUP/EMAIL EXAMPLE
-----------------------------------------------------
    WITHOUT Kafka (in-memory queue):
      signup() -> pushes task into RAM queue -> server crashes -> task LOST

    WITH Kafka:
      signup() -> publishes "send-welcome-email" message to Kafka
               -> Kafka writes it to disk (and copies to other machines)
               -> signup() returns, user sees success
               -> [server crashes here - doesn't matter anymore!]
               -> a worker (possibly on a totally different machine, maybe
                  started up fresh after the crash) reads the message from
                  Kafka and sends the email - nothing was lost

WHY YOU MIGHT NOT NEED KAFKA
-----------------------------------------------------
It's worth being honest: Kafka is a whole separate system you have to
run, operate, and maintain (or pay a cloud provider to manage for you) -
it's genuinely more complex than just using an in-memory queue inside
your own program. If you're building something small, or the background
task genuinely doesn't matter much if it's occasionally lost (like a
non-critical analytics event), a simple in-memory blocking queue is
often perfectly fine and much simpler. Kafka (or similar tools like
RabbitMQ or AWS SQS) becomes worth the complexity specifically when
losing a message would be a real problem, or when you're operating at a
scale/reliability level where a single process's RAM just isn't good
enough anymore.

ONE-SENTENCE SUMMARY
-----------------------------------------------------
Kafka is a durable, shared message queue that lives outside any single
program - it writes messages to disk (and copies them across machines)
so that messages survive crashes, and it lets multiple independent
programs publish and read from the same stream of messages without
losing anything, unlike an in-memory queue that vanishes the moment its
process dies.
